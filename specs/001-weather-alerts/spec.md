# Спецификация функции: Сервис Weather Alerts

**Ветка функции**: `001-weather-alerts`  
**Создано**: 27 марта 2026 г.  
**Статус**: Черновик  
**Вход**: Описание пользователя: "Создай спецификацию для функции сервиса погоды: Weather Alerts (уведомления о погоде)"

## Уточнения

### Сессия 2026-04-09

- В: Модель подписки → О: Одна подписка принадлежит одному пользователю, одной локации и одному набору условий; у пользователя может быть несколько подписок; подписку можно временно отключить или удалить.
- В: Условия → О: Поддерживаются типы условий temperature_below, temperature_above, rain_probability_above, wind_speed_above и severe_weather; несколько условий в одной подписке работают по логике ANY; severe_weather включает storm, hurricane, tornado, blizzard, extreme_heat и extreme_cold.
- В: Окно времени и расписание → О: Активное окно вычисляется по локальному времени локации; вне окна уведомления ставятся в pending до ближайшего разрешенного окна, если событие все еще актуально; сценарий «дождь завтра» проверяется по daily forecast на следующий календарный день в часовом поясе локации.
- В: Дедупликация → О: Дубликатом считается уведомление для того же пользователя, подписки, канала доставки и типа погодного события в пределах 12 часов; если условие перестало выполняться и снова выполнилось после 12 часов, можно отправить новое уведомление.
- В: Каналы доставки → О: Поддерживаются email, push и webhook; уведомления отправляются во все активные каналы; повторные попытки выполняются с exponential backoff; после исчерпания retries канал помечается как failed.
- В: Производительность и надежность → О: От обнаружения события до первой попытки отправки должно проходить менее 1 минуты; обработка событий идемпотентна; отказ одного канала не блокирует остальные.
- В: Non-goals → О: SMS, сложные деревья правил AND/OR кроме ANY по набору условий подписки, а также историческая аналитика сверх базового delivery log не входят в объем.
- В: Граничные случаи → О: Удаление подписки во время pending или retry отменяет дальнейшие попытки; при недоступности weather provider оценка временно приостанавливается; повторяющиеся ошибки webhook 500 изолированы в рамках канала; неизвестные/неоднозначные локации и некорректные расписания считаются ошибками валидации; одновременное срабатывание нескольких условий дает одно уведомление на канал по правилам dedup.

## Пользовательские сценарии и тестирование

### Пользовательская история 1: Создание и управление подписками (Приоритет: P1)

Пользователь может создать подписку для одной локации и одного набора условий, затем временно отключить или удалить ее без влияния на другие подписки.

**Почему этот приоритет**: Модель подписки является базовой единицей всей логики оповещений.

**Независимый тест**: Создать несколько подписок для одного пользователя на разные локации и условия, отключить одну подписку и убедиться, что остальные продолжают работать.

**Сценарии приемки**:

1. **Допустим** пользователь создает подписку для одной локации с двумя условиями и логикой ANY, **когда** истинным становится только одно условие, **тогда** подписка считается подходящей для отправки уведомления.
2. **Допустим** у пользователя есть две подписки для двух разных локаций, **когда** событие относится только к одной локации, **тогда** оценивается только соответствующая подписка.
3. **Допустим** пользователь временно отключил подписку, **когда** происходит подходящее погодное событие, **тогда** уведомление не отправляется до повторного включения подписки.
4. **Допустим** пользователь удалил подписку, **когда** в будущем происходит подходящее событие, **тогда** уведомления по этой подписке не создаются.

---

### Пользовательская история 2: Оценка погодных условий и расписания (Приоритет: P1)

Пользователь задает поддерживаемые типы условий и активное окно доставки по локальному времени локации.

**Почему этот приоритет**: Эти бизнес-правила определяют, отправлять уведомление сейчас, отложить его или отклонить.

**Независимый тест**: Настроить каждый поддерживаемый тип условия, задать окно расписания и проверить, что уведомление срабатывает, откладывается или отклоняется по правилам.

**Сценарии приемки**:

1. **Допустим** подписка с условием rain_probability_above равным 70%, **когда** прогноз на следующий календарный день для локации показывает 75%, **тогда** уведомление становится кандидатом на доставку.
2. **Допустим** подписка с условием temperature_below равным -10°C, **когда** прогноз достигает -12°C, **тогда** уведомление становится кандидатом на доставку.
3. **Допустим** в подписке включено условие severe_weather, **когда** прогноз фиксирует tornado, hurricane, storm, blizzard, extreme_heat или extreme_cold, **тогда** уведомление становится кандидатом на доставку.
4. **Допустим** подписка имеет окно 08:00-20:00 по локальному времени локации, **когда** событие наступает в 21:00, **тогда** уведомление попадает в pending до следующего разрешенного окна при сохранении актуальности события.
5. **Допустим** пользователь отправляет подписку с некорректным расписанием или неоднозначной локацией, **когда** запрос проходит валидацию, **тогда** система возвращает ошибку валидации.

---

### Пользовательская история 3: Доставка и повторы уведомлений (Приоритет: P1)

Пользователь получает уведомления по всем активным каналам, а временный сбой одного канала не блокирует остальные.

**Почему этот приоритет**: Надежная доставка — ключевое обещание функции.

**Независимый тест**: Настроить email, push и webhook в одной подписке, искусственно уронить один канал и проверить, что остальные каналы доставляют уведомления.

**Сценарии приемки**:

1. **Допустим** подписка имеет активные email, push и webhook, **когда** срабатывает условие, **тогда** система пытается отправить уведомление во все активные каналы.
2. **Допустим** webhook возвращает HTTP 500, **когда** запускаются повторы, **тогда** используется exponential backoff, а канал получает статус failed после исчерпания retries.
3. **Допустим** email доставлен успешно, а webhook завершился ошибкой, **когда** обработка события завершена, **тогда** ошибка webhook не влияет на доставку в email и push.
4. **Допустим** одно и то же погодное событие обработано повторно, **когда** выполняется повторная оценка, **тогда** система остается идемпотентной и не создает лишние отправки.

---

### Пользовательская история 4: Предотвращение дублей и обработка pending (Приоритет: P2)

Пользователь не должен получать дублирующиеся уведомления для одной подписки, канала и типа погодного события в пределах окна дедупликации.

**Почему этот приоритет**: Дедупликация защищает от спама и повышает доверие к сервису.

**Независимый тест**: Многократно подать одно и то же событие в пределах 12 часов, удалить подписку во время pending и убедиться в корректной отмене.

**Сценарии приемки**:

1. **Допустим** пользователь уже получил уведомление для комбинации подписка+канал+тип события, **когда** то же событие обрабатывается повторно в пределах 12 часов, **тогда** повторное уведомление по этому каналу не отправляется.
2. **Допустим** условие перестало выполняться и снова стало истинным позже чем через 12 часов, **когда** событие наступает повторно, **тогда** разрешена новая отправка.
3. **Допустим** уведомление находится в pending из-за закрытого окна, **когда** пользователь удаляет подписку до открытия окна, **тогда** pending-уведомление отменяется без попытки доставки.
4. **Допустим** в одной подписке одновременно сработали несколько условий, **когда** система выполняет оценку, **тогда** отправляется не более одного уведомления на канал с учетом правил dedup.

---

### Граничные случаи

- Подписка удалена во время pending или retry: все последующие попытки отменяются немедленно, в журнале сохраняется запись о результате.
- Weather provider недоступен: новые результаты оценки не создаются до восстановления источника данных, текущие pending-элементы не повреждаются.
- Webhook стабильно возвращает HTTP 500: повторяется только webhook-канал, остальные каналы продолжают обработку независимо.
- Локация не найдена или неоднозначна: создание или обновление подписки отклоняется ошибкой валидации.
- Пользователь задал некорректное расписание: система отклоняет запрос и не сохраняет изменения.
- Несколько условий сработали одновременно: формируется одно уведомление на канал в рамках одной подписки.
- Окно дедупликации истекло: при повторном выполнении условия после 12 часов допускается новая отправка.

## Ограничения области (Non-Goals)

- Доставка по SMS не входит в объем.
- Сложные деревья правил AND/OR кроме ANY по набору условий в подписке не входят в объем.
- Историческая аналитика и тренды сверх базового журнала доставки не входят в объем.

## Требования

### Функциональные требования

- **FR-001**: Система должна создавать одну подписку для одного пользователя, одной локации и одного набора условий.
- **FR-002**: Система должна позволять пользователю иметь несколько подписок для разных локаций и/или условий.
- **FR-003**: Система должна поддерживать временное отключение, повторное включение и удаление подписки.
- **FR-004**: Система должна поддерживать типы условий temperature_below, temperature_above, rain_probability_above, wind_speed_above и severe_weather.
- **FR-005**: Система должна оценивать несколько условий внутри одной подписки по логике ANY.
- **FR-006**: Система должна интерпретировать severe_weather как storm, hurricane, tornado, blizzard, extreme_heat и extreme_cold.
- **FR-007**: Система должна применять расписание по часовому поясу локации подписки.
- **FR-008**: Система должна переводить уведомление в pending, если событие произошло вне окна доставки, и отправлять его в следующем разрешенном окне, только если событие все еще актуально.
- **FR-009**: Система должна проверять правило «дождь завтра» по daily forecast на следующий календарный день в часовом поясе локации.
- **FR-010**: Система должна отправлять уведомления во все активные каналы подписки.
- **FR-011**: Система должна поддерживать каналы email, push и webhook.
- **FR-012**: Система должна выполнять повторные попытки доставки при временных ошибках с использованием exponential backoff.
- **FR-013**: Система должна устанавливать статус канала доставки failed после исчерпания retries.
- **FR-014**: Система должна предотвращать дубли для комбинации пользователь+подписка+канал+тип погодного события в пределах 12 часов.
- **FR-015**: Система должна разрешать новую отправку после истечения окна дедупликации, если условие снова стало истинным.
- **FR-016**: Система должна обеспечивать идемпотентность при повторной обработке событий.
- **FR-017**: Система должна изолировать сбои каналов, чтобы ошибка одного канала не влияла на остальные.
- **FR-018**: Система должна отклонять некорректные расписания и неизвестные/неоднозначные локации при создании и обновлении подписки.
- **FR-019**: Система должна сохранять базовый журнал доставки для каждой попытки.
- **FR-020**: Система должна корректно обрабатывать недоступность weather provider без порчи pending и retry-состояний.

### Нефункциональные требования

- **NFR-001**: Первая попытка отправки должна стартовать не позднее чем через 1 минуту после обнаружения подходящего события.
- **NFR-002**: Повторная обработка одного и того же события должна быть идемпотентной.
- **NFR-003**: Сбой одного канала не должен ухудшать доставку по другим каналам в той же подписке.
- **NFR-004**: Система должна масштабироваться при большом количестве активных подписок без нарушения целевого времени первой попытки отправки.
- **NFR-005**: Система должна обеспечивать надежную стратегию retries для временных ошибок доставки.

### Ключевые сущности

- **Subscription**: Конфигурация оповещений пользователя для одной локации. Содержит пользователя, локацию, состояние, расписание и метаданные.
- **Condition Set**: Набор условий в подписке с типами, порогами и режимом ANY.
- **Delivery Channel**: Назначение уведомлений с типом канала, адресом/endpoint, статусом активности и retry-метаданными.
- **Pending Notification**: Уведомление, отложенное до открытия окна доставки.
- **Delivery Log Entry**: Базовая запись о попытке/пропуске/ошибке/успехе доставки.
- **Weather Event**: Нормализованное погодное событие для оценки правил.

## Критерии успеха

### Измеримые результаты

- **SC-001**: Для не менее 95% подходящих событий первая попытка отправки начинается менее чем за 1 минуту.
- **SC-002**: В тестах отсутствуют дубли в пределах 12-часового окна для комбинации пользователь+подписка+канал+тип события.
- **SC-003**: Не менее 99% временных ошибок каналов проходят по политике retries до установки failed.
- **SC-004**: Не менее 95% операций create/disable/enable/delete по подпискам завершаются менее чем за 5 секунд.
- **SC-005**: Система сохраняет стабильную оценку алертов под конкурентной нагрузкой активных подписок без нарушения целевого времени первой попытки отправки.
- **SC-006**: Не менее 90% подходящих уведомлений доставляются во все активные каналы при отсутствии ошибок каналов.

## Предположения

- Пользователи имеют доступ к основному weather REST API для данных по локациям и прогнозам.
- Текущая система аутентификации переиспользуется для идентификации владельца подписки.
- Интеграции email, push и webhook доступны в инфраструктуре.
- Часовой пояс локации доступен напрямую или вычисляется из модели локации.
- Для текущего объема достаточно базового delivery log без продвинутой аналитики.

## Поток данных и дизайн API

### Эндпоинты управления подписками

- `POST /api/v1/subscriptions` — создать подписку
- `GET /api/v1/subscriptions` — получить список подписок пользователя
- `GET /api/v1/subscriptions/{subscriptionId}` — получить подписку по идентификатору
- `PATCH /api/v1/subscriptions/{subscriptionId}` — обновить условия, каналы или расписание
- `POST /api/v1/subscriptions/{subscriptionId}/disable` — временно отключить подписку
- `POST /api/v1/subscriptions/{subscriptionId}/enable` — включить подписку
- `DELETE /api/v1/subscriptions/{subscriptionId}` — удалить подписку

### Пример payload для создания подписки

```json
{
  "location": {
    "id": "location-id-or-normalized-key"
  },
  "conditions": [
    {
      "type": "rain_probability_above",
      "threshold": 70
    },
    {
      "type": "temperature_below",
      "threshold": -10
    }
  ],
  "conditionMode": "ANY",
  "schedule": {
    "timezone": "location",
    "activeFrom": "08:00",
    "activeTo": "20:00"
  },
  "deliveryChannels": [
    { "type": "email", "address": "user@example.com", "active": true },
    { "type": "push", "token": "push-token", "active": true },
    { "type": "webhook", "url": "https://example.com/webhook", "active": true }
  ]
}
```

### Пример payload записи доставки

```json
{
  "subscriptionId": "sub_123",
  "weatherEventType": "rain_probability_above",
  "channel": "email",
  "outcome": "delivered",
  "attemptCount": 1,
  "timestamp": "2026-04-09T10:00:00Z"
}
```

### Поток срабатывания алерта

1. Система получает weather event или данные прогноза от weather provider.
2. Событие нормализуется до типа, пригодного для оценки подписок.
3. Находятся активные подписки для затронутой локации.
4. Для каждой подписки условия проверяются в режиме ANY.
5. Если окно доставки закрыто, уведомление сохраняется в pending.
6. Если окно открыто и dedup не блокирует отправку, запускается доставка во все активные каналы.
7. Для каждого канала применяется собственная политика retries с exponential backoff.
8. Для каждого шага пишется запись в delivery log.
9. Повторная обработка того же события не должна создавать дубли в пределах dedup window.

### Пример структуры уведомления

```json
{
  "subscriptionId": "user-subscription-id",
  "location": "Moscow, Russia",
  "condition": {
    "type": "temperature_below",
    "threshold": -10,
    "unit": "C"
  },
  "forecastData": {
    "timestamp": "2026-03-27T14:30:00Z",
    "temperature": -12,
    "rainProbability": 0.45,
    "windSpeed": 8
  },
  "message": "Temperature alert: forecast shows -12°C, your threshold was -10°C",
  "timestamp": "2026-03-27T14:31:00Z"
}
```
