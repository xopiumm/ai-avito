# Исследование: Weather Alerts

## Выборы по стеку

### FastAPI + Pydantic

**Решение**: Использовать FastAPI как REST API слой и Pydantic v2 для схем/валидации.

**Обоснование**: Хорошая поддержка async, автоматическая публикация OpenAPI, удобная валидация payload и минимальный объем инфраструктурного кода.

**Рассмотренные альтернативы**:
- Django REST Framework: больше накладных расходов для данного объема.
- Flask: потребовал бы больше ручной сборки вокруг схем и документации.

### PostgreSQL + SQLAlchemy + asyncpg

**Решение**: Хранить подписки, состояния и delivery logs в PostgreSQL; доступ реализовать через SQLAlchemy 2.x async engine и asyncpg.

**Обоснование**: Нужны транзакционность, согласованность и надежная фиксация статусов для идемпотентности и аудита доставки.

**Рассмотренные альтернативы**:
- SQLite: подходит для локальной отладки, но ограничен для конкурентной production-обработки.
- NoSQL-only подход: усложняет транзакционную модель и консистентность критичных операций.

### Redis для deduplication и координации

**Решение**: Использовать Redis для dedup keys, pending coordination и короткоживущего operational состояния.

**Обоснование**: Нативный TTL, атомарные операции, низкая латентность для горячего пути проверки дублей.

**Рассмотренные альтернативы**:
- Только PostgreSQL: возможно, но менее эффективно для частых dedup-проверок.
- Kafka-first архитектура: избыточна для текущего объема.

### Celery + Redis для фоновой доставки

**Решение**: Использовать Celery workers для fanout и retries с Redis broker/backend.

**Обоснование**: Удобная модель отложенных задач и повторов, изоляция каналов, масштабируемые воркеры.

**Рассмотренные альтернативы**:
- RQ: проще, но менее гибко в retry-политиках.
- Кастомная очередь на asyncio: выше стоимость поддержки.

## Архитектура компонентов

### 1. API слой

- Управление жизненным циклом подписок: create/list/get/update/disable/enable/delete.
- Валидация входа: локации, расписания, условий, каналов.

### 2. Domain/Service слой

- SubscriptionService: операции с подписками.
- ConditionEvaluationService: проверка условий и логики ANY.
- ScheduleService: проверка активного окна по timezone.
- DeduplicationService: управление dedup-ключами в Redis.
- NotificationOrchestrator: fanout и агрегация результатов доставки.

### 3. Integration adapters

- Адаптер weather provider.
- Адаптер email.
- Адаптер push.
- Адаптер webhook.

### 4. Worker слой

- Воркер оценки событий.
- Воркеры доставки по каналам.
- Воркеры повторных попыток.

## Стратегия deduplication

**Решение**: Ключ dedup строится из user_id + subscription_id + channel + weather_event_type и хранится в Redis с TTL 12 часов.

**Обоснование**: Полностью соответствует бизнес-правилу и дает предсказуемую производительность на горячем пути.

**Примечания по реализации**:
- Ключ создается до отправки, чтобы снизить риск гонки.
- При наличии ключа отправка по соответствующему каналу пропускается.
- После TTL отправка снова разрешается при повторном выполнении условия.

## Стратегия retries

**Решение**: Exponential backoff для временных ошибок с ограничением числа повторов; после исчерпания — статус failed.

**Обоснование**: Снижает нагрузку на нестабильные интеграции, не блокирует другие каналы и улучшает общую надежность.

**Примечания по реализации**:
- Политика retries независима для каждого канала.
- Timeout и 5xx считаются временными ошибками.
- Невосстановимые ошибки обрабатываются без бесконечных повторов.

## Наблюдаемость

**Решение**: Структурированные JSON-логи, correlation id, метрики и трассировка.

**Обоснование**: Сервис чувствителен к latency и дедупликации, поэтому нужна сквозная наблюдаемость по всей цепочке.

**Ключевые сигналы**:
- Время event-to-first-attempt.
- Success/failure по каналам.
- Retry exhaustion.
- Dedup hit rate.
- Объем pending.
- Ошибки внешнего provider.

## Стратегия тестирования

**Решение**: Unit + integration + contract tests.

**Обоснование**: Соответствует конституции (TDD и фокус на интеграции), покрывает рискованные зоны бизнес-логики.

**Слои тестов**:
- Unit: правила условий, расписание, dedup, backoff, идемпотентность.
- Integration: жизненный цикл подписки и путь доставки от события до каналов.
- Contract: совместимость request/response и внутренних событийных payload.

## Риски

- Гонки при конкурентной обработке одинаковых событий.
- Ошибки на границах часовых поясов и переходов DST.
- Накопление pending при длительной недоступности weather provider.
- Риск блокировки pipeline при ошибках webhook без изоляции каналов.
